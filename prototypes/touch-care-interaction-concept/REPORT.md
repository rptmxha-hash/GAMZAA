# Concept Prototype Report: 터치 케어 인터랙션 (Touch Care Interaction)

> **Date**: 2026-07-09
> **Prototype Path**: Engine (Unity 6.5)
> **Concept File**: design/gdd/game-concept.md

---

## Hypothesis

플레이어가 창문 드래그·난로 롱프레스·물뿌리개 세 아날로그 제스처를 (번짐 반응 + ASMR
사운드 피드백과 함께) 수행하면, 터치 그 자체가 명상적·위안적으로 느껴질 것이다 — 이는
테스터가 자유롭게 플레이해보라고 했을 때, 기능적으로 불필요한데도 제스처를 반복하거나
유도 없이 "차분하다/기분 좋다" 같은 표현을 자발적으로 쓰는 것으로 확인된다.

---

## Riskiest Assumption Tested

이 게임 전체의 중심 베팅 — **아날로그 터치 자체(게임 시스템이 아니라 "만지는 행위" 그
자체)가 감정적 무게를 가질 수 있는가**. 시스템 인덱스(`design/gdd/systems-index.md`)에서
이미 최고위험 시스템으로 식별된 항목.

## Approach

Unity 6.5(2D URP) 프로젝트를 `prototypes/touch-care-interaction-concept/`에 새로 생성.
씬 전체(카메라·흙바닥·창문·난로·물뿌리개)를 런타임에 코드로 자동 구성하는 부트스트랩
스크립트 1개 + 제스처 스크립트 2종(드래그/롱프레스) + 공유 번짐 이펙트 + 절차적 사운드
생성기로 구성. 씬(.unity) 파일을 직접 편집하지 않고 코드 생성 방식을 택해 손상 위험을
피함.

**Path chosen:** Engine (Unity)
**Reason for path:** 가설이 "이 로직이 맞는가"가 아니라 "이 손맛이 좋은가"를 묻는
질문이라, 브라우저 지연시간이 결과를 왜곡할 수 있는 HTML 경로 대신 실제 출시 엔진에서
직접 검증.

**Shortcuts taken (intentional):**
- 감자·날씨·생장 단계·수치 상태 전부 없음 — 순수하게 3개 제스처의 터치 반응만 존재
- 아트는 전부 코드 생성 단색 도형(원/사각형) — 수채 텍스처·번짐 질감 없음
- 사운드는 실제 ASMR 녹음이 아니라 런타임 절차적 생성 톤(사인파+화이트노이즈 기반) —
  응답 타이밍 검증용이며 사운드 자체의 정서적 질감은 검증 대상에서 제외
- 세이브·오프라인 계산·광고·UI 메뉴 전부 없음
- 반복 테스트를 위해 창문 열림/닫힘에 히스테리시스를 둬 무한 재시도 가능하게 함

## Result

**창문(드래그)와 물뿌리개(드래그)**: 번짐 이펙트와 절차 사운드는 정상 작동했으나,
테스터가 "열리는 느낌이 안 난다" / "물이 뿌려지는 느낌이 안 난다"고 명확히 지적함 —
제스처의 시각 피드백이 해당 동작(창문을 연다, 물을 뿌린다)을 은유하지 못했다는 뜻.

**난로(롱프레스)**: 세 제스처 중 유일하게 "난로 같았다"는 긍정 반응을 얻음. 핵심 차이는
난로만 "서서히 차오르다가 완성되는" 방사형 글로우 진행 피드백을 가졌다는 점 — 창문/
물뿌리개는 위치 이동에 따른 일반적인 번짐 퍼프만 있어 그 자체로는 "열림"이나 "물주기"를
표상하지 못함.

**전반적 반응**: 테스터의 표현은 "나쁘지 않았다", "무난"이었으며, 자발적으로 제스처를
반복하는 모습이나 예상 밖의 서프라이즈는 관찰되지 않음 — 강한 긍정 신호는 아니지만
명확한 거부 신호도 아님.

**사운드**: 테스터가 "이질감이 든다"고 명시적으로 지적 — 예상된 결과(절차적 placeholder
톤은 애초에 진짜 ASMR을 대체하지 않음)이며, 테스터도 이를 "아트·사운드가 실제로 붙으면
해결될 문제"로 이해하고 있었음.

> 인용: "물뿌리개가 물이 뿌려지는 느낌이 안 나고. 창문도 열리는 느낌은 당연히 안 나.
> 난로만 그나마 난로같았다." / "터치 손맛 컨셉 자체는 유효하고, 창문/물뿌리개 피드백은
> 실제 아트랑 사운드가 붙어야 더 정확히 피드백 될 거 같아."

## Recommendation: PROCEED

터치 손맛 컨셉 자체는 유효하다고 판단(사용자 확정). 창문·물뿌리개가 "느낌이 안 난다"는
지적은 손맛 자체의 실패가 아니라 **이 프로토타입의 placeholder 아트/사운드 한계** —
실제 수채 번짐 텍스처와 실제 ASMR 사운드가 붙으면 해결될 문제로 판단해 PROCEED. 단,
아래 "If Proceeding"에 명시된 발견 사항은 GDD 작성 시 반드시 반영해야 함.

## If Proceeding

- **Core tuning values discovered:**
  - 창문 드래그 완료 임계값 약 65% 이동거리 + 35% 히스테리시스로 재시도 가능 — 반복
    테스트에 문제없이 작동함(수치 자체는 임시지만 "히스테리시스로 반복 가능하게" 하는
    구조는 유효)
  - 난로 롱프레스 완료 시간 약 1.2초 — 이 정도 길이의 "서서히 차오름"이 손맛을 만드는 데
    충분해 보임(정밀 튜닝은 실제 아트 붙은 뒤 재검증 필요)

- **Assumptions confirmed:**
  - "충분히 눌렀다"는 신호를 숫자 카운트다운이 아니라 **시각적 완성(글로우가 다 찼을
    때)**으로 주는 방식이 실제로 작동함 — Section 7(UI/HUD)이 이미 정한 "숫자 카운트다운
    금지" 규칙을 뒷받침하는 실증

- **Assumptions disproved / needs redesign:**
  - **창문과 물뿌리개는 단순 "위치 이동 + 일반 번짐 퍼프"만으로는 그 동작(열림/물주기)을
    표상하지 못한다.** 난로처럼 "그 동작에 고유한 진행형 피드백"이 필요함 — 예를 들어
    창문은 안개가 걷히는 시각적 변화, 물뿌리개는 물방울 파티클이 흙에 튀는 표현 등, 동작
    고유의 은유가 있어야 함. GDD 작성 시 이 세 제스처를 "동일한 드래그 로직의 변형"으로
    뭉뚱그리지 말고, 각각 고유한 진행/완성 신호를 설계할 것.

- **Emergent mechanics:**
  - 난로의 "누르는 동안 서서히 차오르는 글로우 + 완성 시 확산되는 큰 번짐" 패턴은 세
    제스처 모두에 적용 가능한 일반 원칙으로 승격할 만함 — "차오름(진행) → 완성(확산)"
    이라는 2단계 피드백 구조 자체가 이 게임의 손맛 문법이 될 수 있음.

> Note: 이 프로토타입은 Engine 경로로 실행되어 손맛을 직접 검증했으나, 아트/사운드가

## Lessons Learned

- **What assumptions were broken by actually building this?**
  콘셉트 문서는 세 제스처를 "아날로그 터치"라는 하나의 카테고리로 뭉뚱그렸지만, 실제로
  만들어보니 제스처마다 **그 동작 고유의 진행형 피드백이 있어야** 손맛이 산다는 게
  드러남 — "드래그"라는 입력 방식이 같다고 피드백 설계까지 같아도 되는 게 아니었음.

- **What surprised us that didn't show up in the brainstorm?**
  난로만 유독 "그럴듯하다"는 반응을 얻은 것 — 브레인스토밍 단계에선 세 제스처를 동등하게
  다뤘지만, 실제로는 "서서히 차오르다 완성되는" 방사형 진행 피드백을 가진 제스처만
  설득력이 있었음. 이건 앞으로 이 게임의 손맛 설계 전체를 관통하는 원칙이 될 수 있음.

- **What would we test differently next time?**
  Placeholder가 아닌 실제 수채 번짐 텍스처와 실제 녹음된 ASMR 사운드로 창문·물뿌리개만
  짧게 재검증하면, "동작을 표상하는 진행형 피드백"을 추가했을 때 실제로 개선되는지 훨씬
  명확히 확인할 수 있을 것.
