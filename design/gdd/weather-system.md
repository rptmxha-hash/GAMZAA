> **Author**: user + systems-designer + art-director
> **Last Updated**: 2026-07-15
> **Implements Pillar**: Pillar 1 (손끝의 위안), Pillar 4 (짧게 자주 부담없이)

## Overview

날씨 시스템은 감자 상태 관리가 노출하는 세 스탯(수분·습도·온도)에 시간에 따른 압력을
가하는 보이지 않는 시계이자, 동시에 플레이어가 매번 앱을 열 때 "오늘은 무슨 날씨지?"
라고 가장 먼저 확인하게 되는 이 게임의 첫인상이다. 24시간 백그라운드로 흘러가는 날씨
체인저가 4종(맑음/폭우안개/한파폭설/폭염) 중 하나를 선택해 감자 상태 관리의 해당
스탯에 압력을 가하고, 동시에 아트 바이블이 이미 정의한 무드·색·에너지로 화면 전체의
톤을 바꾼다. 이 시스템이 없다면 감자는 늘 같은 상태로 정지해 있을 뿐이고, 대처할
이유도 손끝의 위안을 느낄 계기도 사라진다.

## Player Fantasy

날씨가 바뀌는 순간, 플레이어는 화면을 열자마자 "아, 오늘은 이런 날이구나"를 몸으로
먼저 느낀다 — 안개 낀 창밖의 차분한 빛, 눈 쌓인 고요, 쨍한 폭염의 눈부심. 이건 정보
전달이 아니라 감자와 함께 그날의 날씨를 겪는 경험이다. Pillar 1(손끝의 위안)이
여기서 시작된다 — 날씨가 감자를 압박하기 때문에 비로소 손끝의 대처가 의미를 갖고,
그 대처가 곧 위안이 된다. 하지만 Pillar 4(짧게 자주 부담없이)에 따라 날씨는 결코
플레이어를 다급하게 만들지 않는다 — 매번 앱을 열 때마다 "오늘 날씨 뭐지?" 확인하는
습관 자체가 이 게임을 찾는 이유의 일부가 되어야 한다.

## Detailed Design

> *(전문 에이전트 미상담 — lean 모드. Section D·H만 lean에서도 상담 필수.)*

### Core Rules

1. **단일 활성 날씨**: 한 번에 4종(맑음/폭우안개/한파폭설/폭염) 중 하나만 활성. MVP
   범위는 3종(맑음/폭우안개/한파) — 폭염은 이후 추가(game-concept.md 스코프 티어와
   일치).
2. **지속시간 기반 스케줄**: 각 날씨는 일정 지속시간을 가지며, 만료되면 다음 날씨를
   선택해 전이한다(선택 로직은 Formulas에서).
3. **감자 상태 관리로의 압력 전달**: 활성 날씨는 자신이 겨냥하는 스탯에
   `potato-stat-system.md` Formulas §2가 이미 정의한 `ACTIVE_RATE`(±2.5/hr)를 그대로
   적용해 `AdjustX(delta)`를 호출한다 — 이 GDD가 새 감쇠율 체계를 만들지 않고 기존
   것을 그대로 소비한다.
4. **벽시계 기반 결정론적 스케줄**: 오프라인에도 날씨가 흘러야 하므로, 이 시스템은
   "주어진 시각에 어떤 날씨였는가"를 프레임 누적이 아니라 벽시계 시각으로부터
   **결정론적으로 재구성**할 수 있어야 한다 — 오프라인 진행 계산(15)이 이 계약에
   의존한다.
5. **세이브 연동**: 날씨 스케줄의 기준점(시드·시작 시각)만 세이브/영속성에 등록하면
   되고, 매 순간의 날씨 자체는 그 기준점으로부터 항상 재계산 가능해야 한다(별도로
   "현재 날씨"를 세이브할 필요 없음).

### States and Transitions

이 시스템의 "상태"는 곧 현재 활성 날씨다.

| 상태 | 진입 조건 | 이탈 조건 |
|---|---|---|
| **Sunny(맑음)** | 초기값 또는 이전 날씨 만료 후 선택됨 | 지속시간 만료 → 다음 날씨 선택 |
| **RainFog(폭우/안개)** | 이전 날씨 만료 후 선택됨 | 지속시간 만료 → 다음 날씨 선택 |
| **ColdSnap(한파/폭설)** | 이전 날씨 만료 후 선택됨 | 지속시간 만료 → 다음 날씨 선택 |
| **Heatwave(폭염, post-MVP)** | 이전 날씨 만료 후 선택됨(MVP 이후 활성화) | 지속시간 만료 → 다음 날씨 선택 |

### Interactions with Other Systems

| 시스템 | 관계 | 인터페이스(잠정) |
|---|---|---|
| 감자 상태 관리 | 이 시스템이 호출(피호출자) | `AdjustMoisture/Humidity/Temperature(delta)` — potato-stat 기존 API 그대로 사용 |
| 세이브/영속성 시스템 | 이 시스템이 등록(호출자) | `Register("weather_schedule_seed", ...)` — 날씨 자체가 아니라 재계산 기준점만 저장 |
| 오프라인 진행 계산 | 이 시스템에 의존(호출자) | `GetWeatherAt(timestamp)` — 임의 시각의 날씨를 결정론적으로 조회 |

### 0. 결정론적 난수 원시 함수 (PRNG 계약)

날씨 지속시간(§1)과 다음 날씨 선택(§2)이 모두 이 함수를 거쳐 생성된다 — 실시간
시뮬레이션이 아니라 시드로부터 언제든 재계산 가능해야 하므로, 이 시스템의 모든
무작위성은 예외 없이 이 원시 함수 하나로 수렴한다.

`H(seed, n, salt) = PRNG_UNIFORM(seed, n, salt) ∈ [0, 1)`

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 스케줄 시드 | `seed` | uint64 (const, 세이브당 1개) | 세이브 생성 시 1회 생성 | 세이브·영속성 시스템이 `weather_schedule_seed`로 등록하는 값의 일부 |
| 구간 인덱스 | `n` | int | 0 이상 정수 | 몇 번째 날씨 구간인지(0=최초 날씨) |
| 스트림 구분자 | `salt` | enum {`'dur'`, `'sel'`} | 2가지 | 지속시간 스트림과 선택 스트림을 서로 독립시키기 위한 구분값 |
| 결과 | `H` | float | [0, 1) | 균등분포 의사난수 1개 |

**Output Range:** [0, 1) 균등분포, 하한 포함·상한 미포함. 같은 `(seed, n, salt)` 입력에는
항상 같은 출력 — 벽시계 재시작·오프라인 갭과 무관하게 결정론적.

**Example:** `seed=42`, `n=5`, `salt='dur'` → `H(42,5,'dur')=0.42`(예시값 — 아래 §1
예제가 그대로 사용).

> **구현 참고**: 구체적 해시 알고리즘(splitmix64, xxhash 등 시드 혼합 함수)은 이 GDD의
> 범위 밖 — `lead-programmer`/`technical-director` 소관. 이 GDD가 잠그는 것은 계약
> (같은 입력 → 같은 출력, 균등분포, `salt`별 독립)뿐이다.

### 1. 날씨 지속시간

각 날씨 구간의 길이는 6~10시간 사이 균등분포로 뽑는다. 평균 8시간은 하루 2~3회
확인하는 Pillar 4 체크인 리듬과 맞아떨어져, 앱을 열 때마다 대략 "지난번과 다른 날씨"를
마주칠 확률이 높으면서도(정적이지 않음), 한 세션 안에 날씨가 여러 번 바뀌어 버리는
일은 드물게 만든다(혼란스럽지 않음). MVP 3종·post-MVP 4종 모두 같은 범위를 공유한다
— 빈도 차등은 §2의 선택 가중치가 전담하므로, 지속시간까지 스탯별로 나누면 튜닝 노브가
중복된다.

`Duration(n) = DURATION_MIN + H(seed, n, 'dur') × (DURATION_MAX - DURATION_MIN)`

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 최소 지속시간 | `DURATION_MIN` | float (const) | 6 (hr) | 날씨 구간 최소 길이 |
| 최대 지속시간 | `DURATION_MAX` | float (const) | 10 (hr) | 날씨 구간 최대 길이 |
| 구간 인덱스 | `n` | int | 0 이상 | §0과 동일 |
| 결과 | `Duration(n)` | float | [6, 10] (hr) | `n`번째 날씨 구간의 길이 |

**Output Range:** [6, 10)시간(§0의 `H∈[0,1)` 반열림 컨벤션 상속 — 10h 자체는 도달
불가), 평균 8시간. 최댓값(10h 미만)조차 potato-stat §6에서 가장
빠른 단독 시듦 시각(습도, 18.65h)의 절반 수준이라 — 단일 날씨 구간 하나만으로는(터치
없이도) 어떤 스탯도 시들게 할 수 없음이 보장된다(의도된 안전 속성, Pillar 3와 일치).

**Example:** `seed=42`, `n=5`, `H(42,5,'dur')=0.42`(§0) → `Duration(5) = 6 + 0.42×4 =
7.68시간`.

### 2. 다음 날씨 선택 (가중치 + 연속 반복 금지)

맑음은 아트 바이블상 유일하게 전용 "위기 포즈"가 없는 날씨(생기 포즈만 가짐,
potato-stat Visual/Audio Requirements 범위 밖으로 명시)라 서사적으로도 "쉬어가는
날"에 해당한다 — 선택 가중치도 이를 반영해 맑음을 나머지보다 높게 둔다. 폭염은
§4에서 확정하듯 넷 중 가장 급격한 압박(`ACTIVE_RATE_HEATWAVE=-4.0`)을 주므로, 심각도와 발생
빈도를 반비례시켜(강렬한 이벤트일수록 드물게) Pillar 4를 지킨다. 직전 날씨와 동일한
날씨가 연속으로 다시 뽑히는 것은 명시적으로 금지한다 — 안 그러면 "맑음이 20시간
연속" 같은 정적인 구간이 통계적으로 발생해 "매번 다른 날"이라는 첫인상 약속이 깨진다.

`P(w_{n+1}=X | w_n) = WEIGHT_X / Σ_{Y: target(Y)≠target(w_n)} WEIGHT_Y`
(단, `target(X) ≠ target(w_n)`) — 선택은 `H(seed, n+1, 'sel')`을 이 CDF에 매핑해 결정.

> **정정(시뮬레이션 검증 반영, 2026-07-11)**: 제외 기준은 날씨 **종류**가 아니라
> **겨냥 스탯**(`target(·)`)이다. MVP 3종은 서로 겨냥 스탯이 겹치지 않으므로
> `target(X)≠target(w_n) ⟺ X≠w_n`이라 수치 변화가 전혀 없다 — 이 정정이 실제로
> 의미를 갖는 건 폭염(post-MVP)이 맑음과 똑같이 수분을 겨냥하기 때문이다. 원래
> "종류만 다르면 통과"로 적었을 때 `맑음→폭염→맑음→폭염...` 교차가 규칙을 문자
> 그대로는 통과하면서도 취지(스탯 다양성 강제)를 무력화해, 수분을 사실상 연속으로
> 몰아붙일 수 있는 허점이 있었다(아래 시뮬레이션 참고).

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 날씨별 기본 가중치 | `WEIGHT_X` | float (const, 날씨별) | 아래 표 | 연속 반복 금지 적용 전, 원시 가중치 |
| 직전 날씨 | `w_n` | enum | {Sunny, RainFog, ColdSnap, (Heatwave)} | `n`번째 구간의 날씨 |
| 겨냥 스탯 | `target(·)` | function | 날씨→스탯 | 맑음/폭염→수분, 폭우안개→습도, 한파→온도(폭염·맑음이 스탯을 공유) |
| 조건부 확률 | `P(w_{n+1}=X\|w_n)` | float | [0,1] | 직전 날씨의 겨냥 스탯과 다른 스탯을 겨냥하는 날씨 중 `X`가 선택될 확률 |

| 날씨 | MVP 가중치(3종) | post-MVP 가중치(4종) | 근거 |
|---|---|---|---|
| Sunny(맑음) | **0.50** | **0.45** | 유일하게 전용 위기 포즈가 없는 "쉬어가는 날" |
| RainFog(폭우/안개) | 0.25 | 0.20 | 표준 이벤트 날씨 |
| ColdSnap(한파/폭설) | 0.25 | 0.20 | 표준 이벤트 날씨 |
| Heatwave(폭염, post-MVP) | — | **0.15** | 넷 중 가장 급격(§4)하므로 가장 희소하게 |

**Output Range:** 각 조건부 확률은 [0,1], 같은 `n`에서 가능한 모든 `X≠w_n`의 합은
항상 정확히 1(재정규화로 보장). 직전 날씨 자신의 확률은 항상 정확히 0.

**Example (MVP, 3종):** `w_5=RainFog`. 제외 후 남은 후보 {Sunny(0.50),
ColdSnap(0.25)}, 합계 0.75 → 재정규화 `Sunny'=0.667`, `ColdSnap'=0.333`. CDF:
`[0,0.667)→Sunny`, `[0.667,1.0)→ColdSnap`. `H(seed,6,'sel')=0.83` →
`Weather_6=ColdSnap`.

> **최초 날씨(`n=0`) 예외**: `Weather_0`은 시드와 무관하게 항상 **Sunny로 고정**한다
> (신규 세이브 첫인상은 항상 "쉬어가는 날" — potato-stat Edge Cases의 "최초 실행 =
> 전 스탯 IDEAL" 관대한 시작 철학과 동일선상). `n=0`에는 `H(seed,0,'sel')`을 소비하지
> 않는다 — 이후 스트림 정렬에 영향 없음.

### 3. 시드로부터의 결정론적 재구성 — `GetWeatherAt(T)`

오프라인 갭이 며칠이어도 "그 시각에 무슨 날씨였는가"를 초 단위로 시뮬레이션하지
않고, 구간 수(`n`)에 비례하는 루프 한 번으로 답한다 — 평균 지속시간 8h이므로 1년
(8760h) 갭이어도 약 1,095회 반복에 불과해 오프라인 배치 계산에 안전하다.

```
GetWeatherAt(seed, scheduleStartUtc, T):
    n ← 0
    segStart ← scheduleStartUtc
    weather ← Sunny                         // Weather(0), §2 예외 규칙
    loop:
        d ← Duration(n)                      // §1
        if segStart + d > T: return (weather, segStart, segStart + d)
        segStart ← segStart + d
        weather ← SelectNext(weather, H(seed, n+1, 'sel'))   // §2
        n ← n + 1
```

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 스케줄 시드 | `seed` | uint64 | — | §0과 동일, `weather_schedule_seed`의 일부 |
| 스케줄 기준 시각 | `scheduleStartUtc` | timestamp | — | `Weather(0)`(Sunny) 시작 시각, `weather_schedule_seed`의 나머지 일부(세이브 생성 시 1회 기록) |
| 조회 시각 | `T` | timestamp | `scheduleStartUtc` 이상 | 임의 UTC 시각 |
| 결과 | `(weather, segStart, segEnd)` | (enum, timestamp, timestamp) | — | `T`를 포함하는 구간의 날씨와 그 구간의 시작·끝 시각 |

**Output Range:** 루프 반복 횟수 상한은 `⌈(T - scheduleStartUtc) / DURATION_MIN⌉`
(최악의 경우 모든 구간이 최소 6h) — 100년 갭이라도 약 146,000회, 수 밀리초 내 완료.
`GetWeatherSegments(fromT, toT)`(오프라인 진행 계산용 배치 변형)는 같은 루프를
`segStart < toT`까지 계속하며 겹치는 구간들을 리스트로 수집하면 되고, 이 목록이
potato-stat §4가 요구하는 "날씨 전환 시각에서 분할" 지점을 정확히 제공한다.

**Example:** `scheduleStartUtc=2026-07-01T00:00Z`, `seed=42`. `Duration(0)=8.10h` →
구간0 `[00:00,08:06]`=Sunny. `Duration(1)=6.40h`, `SelectNext(Sunny,·)=RainFog` →
구간1 `[08:06,14:30]`=RainFog. `Duration(2)=9.20h`, `SelectNext(RainFog,·)=ColdSnap`
→ 구간2 `[14:30,23:42]`=ColdSnap. 조회 `T=2026-07-01T20:00Z` → 루프가 `n=2`에서
멈춤 → 결과 `(ColdSnap, 14:30, 23:42)`.

### 4. 폭염(Heatwave) `ACTIVE_RATE` 확정 — potato-stat Open Question #1 답변

potato-stat-system.md Formulas §2가 잠근 패턴(`ACTIVE_RATEᵢ` 상수, 스탯별 부호만
다름)을 그대로 따르되, 폭염 전용값을 확정한다. **결론: `ACTIVE_RATE_HEATWAVE = -4.0
pts/hr`(수분 겨냥) — potato-stat의 잠정 제안값을 그대로 확정한다.**

`rate(수분, t) = ACTIVE_RATE_HEATWAVE (폭염 활성 시)` — potato-stat §2의
`rate(Vᵢ,t)` 정의를 그대로 재사용(신규 함수 아님).

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 폭염 활성 감쇠율 | `ACTIVE_RATE_HEATWAVE` | float (const) | **-4.0 pts/hr** | potato-stat §2의 `ACTIVE_RATEᵢ` 패밀리 값(수분 겨냥, 표준 2.5의 1.6배) |

**근거(정합성 검증, potato-stat §6과 동일 방법론 재사용)**: 수분 반폭=25,
`IDEAL=50`, `NEGLECT_K=0.5`(모두 potato-stat 기존 상수, 재정의 아님).

- 극값(0) 도달: `50/4.0 = 12.5h`
- 시듦 시각: 2차 구간 기여 `= (0.5×4.0/2)×6.25² = 39.06`, 이후 등속 구간

습도(18.65h)보다 약 1.3시간(≈7%) 더 빠르고, 경고 구간도 가장 짧다. 동시에

4.0/hr` 권장 범위(potato-stat Tuning Knobs) 상한에 정확히 걸쳐 있어 그 범위를 벗어나지
않는다 — **potato-stat 공식·튜닝 가이드 어느 것도 개정할 필요 없음.**

`clamp(V+Δ,0,100)`가 결과 스탯값을 이미 클램프).

### 5. 날씨 전환 순간의 감쇠율 변화 — potato-stat Open Question #2 답변

**결론: 즉시 전환(instant switch)** — 보간(gradual interpolation) 채택하지 않는다.

`rate(Vᵢ, t) = rate(Vᵢ, n)`, `n = 구간 인덱스(§3의 GetWeatherAt이 반환하는 구간)` —
구간 경계에서 계단함수로 정확히 한 번 바뀌고, 같은 구간 안에서는 상수 유지(potato-stat
§2 규칙 "한 시점에 정확히 하나의 감쇠율만 쓴다"를 전환 경계까지 그대로 확장할 뿐,
신규 규칙 아님).

| Variable | Symbol | Type | Range | Description |
|---|---|---|---|---|
| 구간별 감쇠율 | `rate(Vᵢ, n)` | float (const, 구간 내) | potato-stat `ACTIVE_RATEᵢ`/`BASELINE_RATEᵢ` 중 하나 | `n`번째 구간 동안 스탯 `i`가 쓰는 감쇠율 |
| 구간 경계 시각 | `segStart(n)` | timestamp | §3 참고 | 이 시각 이후 `rate(·, n)`이 즉시 적용됨 |

**근거**:

1. **potato-stat §4의 사다리꼴 닫힌 형식을 보존한다.** §4는 "구간마다 상수 rate →
   `overshoot(t)` 조각별 선형"을 전제한다. 보간을 택했다면 전환 구간의 `overshoot(t)`가
   선형이 아니게 되어 §4·§6·AC-F-14·AC-F-18~20을 전부 재유도해야 했을 것이다 —
   **즉시 전환은 그 재작업을 요구하지 않는다.**
2. **기존 원자적 적용 패턴과 일치한다.** potato-stat §3(터치 보정)이 이미 "피드백은
   진행형·효과는 원자적"이라는 선례를 세워뒀다. 날씨 전환도 동일 철학: **기계적
   감쇠율은 즉시 전환**되지만, **무드·색 크로스페이드 같은 시각 연출은 완전히 별개
   레이어**로 이 GDD의 Visual/Audio Requirements에서 부드럽게 처리할 수 있다.
3. **potato-stat §2 규칙과 정합.** "한 시점에 정확히 하나의 감쇠율" 규칙은 보간
   중간값을 허용하지 않는다 — 즉시 전환만이 이 규칙과 모순 없이 공존한다.

**Output Range:** N/A(이산 전환 규칙) — `rate`는 항상 potato-stat이 정의한 유한 상수
집합(`{±2.5, ±0.5, ±4.0}`, post-MVP 포함) 중 정확히 하나.

**Example:** 습도 스탯, `t=8h`에 폭우/안개(`rate=+2.5`) 종료 → 한파(습도 비겨냥,
`rate=+0.5`) 전환. `V(8⁻)=65`, `V(8⁺)=65`(값은 연속, 순간이동 없음) — 기울기만
`t=8h`에서 꺾인다(kink). `t=14h`: `V(14)=clamp(65+0.5×6,0,100)=68`.

**potato-stat-system.md 개정 필요 여부: 없음.** 위 결정은 §2·§3·§4 어느 공식도
바꾸지 않고 AC-F-06~20을 그대로 유지시킨다 — Open Questions 표 해당 행은 "해결됨 →
날씨 시스템 GDD §5, 즉시 전환 확정, 기존 공식 무변경"으로 갱신만 하면 된다.

### 6. 복합 방치 리스크 검증 — 실제 날씨 회전 하의 시듦 시각

`potato-stat-system.md` §6은 스탯 하나가 고립되어 그 날씨가 무기한 지속된다는
가정으로 시듦 시각을 검증했다. 하지만 실제로는 기본 엔트로피 규칙(모든 스탯이
항상 자기 위기 방향으로 흐름)에 따라 3개 스탯이 동시에 압박받으며 방치 지표가
가산적으로 쌓인다 — 이 절은 §1·§2의 실제 날씨 회전 하에서 그 약속이 유지되는지
검증한다(Monte Carlo 대신, 안전성 주장에는 오히려 더 엄격한 손구성 적대적
시나리오 방식 사용).

| 시나리오 | 구성 | 시듦 시각(T) | 고립 벤치마크(18.65–23h) 대비 |
|---|---|---|---|
| A — 라운드로빈, 최소 지속시간 | 맑음→폭우안개→한파→...(전부 6h) | 26.97h | 더 안전 |
| B — 폭우안개/한파 교차, 최대/최소 | 폭우안개10h↔한파6h[^1] | 25.24h | 더 안전 |
| C — 맑음/폭우안개 교차, 최대/최소 | 맑음 6h(`DURATION_MIN`, 고정)↔폭우안개 10h(`DURATION_MAX`, 고정)[^2] | 24.04h | 더 안전 |
| D — 맑음→폭염 허점(정정 전, 역사적 참고용, **도달 불가**)[^3] | 맑음→폭염→맑음→폭염... | 19.6h | *(제외 — 안전 경계 계산 입력 아님)* |
| E — 정정 후(post-MVP) | 맑음→[스탯 다른 날씨]→폭염→... | ≈22.5h | 더 안전 |
| 평균적 라운드로빈 | 맑음(0-8)→폭우안개(8-16)→한파(16-24) | N(24h)≈24/100 | 시듦과 거리 멂 |

[^1]: **재검증 발견(2026-07-12, qa-lead 정밀 재검증 부수 발견)**: 이 표기는 `t=0`부터
폭우안개로 시작하는 것으로 읽히지만, §2 예외 규칙상 `Weather_0`은 항상 맑음이라
문자 그대로는 도달 불가능한 초기 조건이다(D와 같은 종류의 결함이나 훨씬 경미함 —
폭우안개/한파 교차 자체는 항상 합법이라 로테이션 본체는 문제없고, 시작점만 문제).
올바른 형태는 `맑음 6h(최악의 경우 최소)→폭우안개10h→한파6h→...`다. 이 보정은
수분을 전혀 겨냥하지 않는 로테이션에 6시간의 무해한 지연만 추가하므로 T를
안전한 방향(더 늦게)으로만 이동시킨다 — "더 안전"이라는 결론과 25.24h가 안전
방향의 근사치라는 점은 유지되지만, **정확한 정정 T값 재계산은 이번 패스 범위
밖**이며 후속 검증 권고에 추가한다. 아래 12시간 재검증에서는 이 정정된(도달
가능한) 형태를 사용한다.

[^2]: **시나리오 C 재정정(2026-07-12)**: 원래 "맑음 6~10h"는 범위였을 뿐 고정값이
아니라 재현 불가능했다. 두 극단을 직접 대입해 비교했다(폭우안개는 항상 10h 고정):
맑음=6h(최소) 고정 → **T=24.04h**(정확히 24.0375h); 맑음=10h(최대) 고정 →
T≈24.78h(더 안전 — 최악 아님). **맑음=6h가 항상 더 나쁜 이유(닫힌 형식 근거)**:
수분·습도 두 스탯이 모두 구간을 이탈한 이후에는, 어느 날씨가 활성이든 합산 이탈
증가율이 항상 `2.5(활성)+0.5(비활성 기본율)=3.0/hr`로 날씨 종류와 무관하게
동일하다(맑음 활성 시 수분 2.5+습도 0.5, 폭우안개 활성 시 반대 — 합은 항상 3.0).
따라서 `dN/dt=0.5×3.0=1.5/hr`는 "양쪽 다 이탈" 이후 구간에서 스케줄과 무관하게
고정된다 — **그 지점에 가장 빨리 도달하는 스케줄이 곧 최악의 스케줄**이 된다.
습도(반폭 15)가 수분(반폭 25)보다 좁아 항상 먼저 이탈하므로, 맑음을 최소(6h)로
두어 폭우안개의 상대적 노출 비중을 최대화하는 쪽이 "양쪽 다 이탈" 상태에 가장
빨리 도달하고, 두 극단 계산이 이 예측과 정확히 일치한다(24.04h < 24.78h). **결론:
시나리오 C는 "맑음 6h(고정)↔폭우안개 10h(고정)"로 완전히 고정하며, T=24.04h는
원래 값과 수치상 일치한다(재현 가능한 형태로 확정됐을 뿐 값 자체는 불변).**

[^3]: **도달 불가능성 확인**: `target(맑음)=수분=target(폭염)`이므로 정정된 §2 규칙
(`target(w_{n+1})≠target(w_n)`)이 "맑음 직후 폭염"(및 그 역)의 선택 확률을 항상
정확히 0으로 만든다 — 이 시퀀스는 라이브 시스템에서 애초에 뽑힐 수 없다. D는 §2
정정을 촉발한 **역사적 근거**(정정 전 허점의 증거)로만 표에 남기며, 아래 12시간
안전 경계 계산의 입력에서는 완전히 제외한다 — 대체 근거는 E(정정 후 실제 도달
가능한 최악 패턴)다.

**하루 2회 체크인(12h) 재검증**: 도달 불가능한 D를 제외하고, 도달 가능한 다섯
시나리오(A, B(정정), C(정정), E, 평균적 라운드로빈) 각각에 대해 최초 12시간

가장 빠르게 어떤 스탯이든 구간을 이탈시키는 유일한 경로이기 때문이다(한파를
대신 선택하면 반폭이 더 넓어 12시간 안에 전혀 이탈하지 않고, 폭염은 맑음과 겨냥
스탯이 같아 두 번째 자리에 절대 올 수 없다). **정정된 약속: `N(12h) ≤ 0.90`**
(도달 가능한 모든 시나리오를 통틀어 참 최댓값) — 기존 문서의 "≤12.25"는 도달
불가능한 시나리오 D를 최악치로 잘못 인용한 값이었다. 정정 후 실제 12시간
체크인 안전 여유는 기존 주장보다 **13배 이상 크다**(0.90 vs 12.25, 100 대비
각각 0.9%/12.25%) — MVP·post-MVP 모두 "하루 2회 체크인은 항상 안전"이라는
약속은 원래 주장보다 훨씬 더 강하게 유지된다.

MVP(3종)는 재튜닝 불필요 — 지속시간 상한(최대 10h)이 연속 노출 자체를 물리적으로
막아 고립 벤치마크보다 항상 안전하다. post-MVP 폭염은 위 §2 정정(종류→겨냥 스탯
기준)만으로 해소되며, `NEGLECT_K`·`DURATION_MIN/MAX`·가중치 테이블 중 어느 것도
재조정할 필요가 없다. 이번 재검증(2026-07-12)에서 시나리오 C를 재현 가능한 형태로
고정하고(맑음=6h/폭우안개=10h), 시나리오 D를 안전 경계 계산에서 배제했으며, 부수적으로
시나리오 B의 표기가 `Weather_0=맑음` 고정 규칙과 문자 그대로는 충돌한다는 점도
확인했다(각주 [^1]) — 세 발견 모두 "안전하다"는 결론을 뒤집지 않았고, 오히려 12시간
체크인 안전 여유가 기존 추정(≤12.25)보다 훨씬 크다(≤0.90)는 것을 보여준다.

> **후속 검증 권고**: 위 시나리오는 손으로 구성한 적대적 경우이지 전역 최솟값의
> 형식적 증명은 아니다(단, `N(12h)`의 전역 최댓값 0.90은 §2의 `Weather_0` 고정 규칙과
> 반폭 비교로부터 직접 증명 가능하다 — 위 근거 참고). 코드 실행 환경이 있을 때 수천
> 개 무작위 시드에 대한 Monte Carlo 스윕을 돌려 Schedule E보다 나쁜 경우가 없는지
> 재확인할 것을 권장한다(`lead-programmer`/`technical-director` 소관, 착수를 막는
> 항목은 아님. Open Questions에 등록). **추가로, 시나리오 B의 정확한 재현 가능
> 표기(맑음 선행 세그먼트 포함)를 확정하고 그에 따른 정확한 전체 시듦 시각(T)
> 재계산도 이 후속 작업 범위에 포함할 것을 권장한다**(각주 [^1] 참고 — 현재는
> "더 안전한 방향으로 이동"이라는 정성적 결론만 확인됨, 정량값 미확정).

## Edge Cases

### 결정론 함수 입력 경계 규약

- **If 조회 시각 `T`가 `scheduleStartUtc`보다 이전이면**: 정의되지 않은 입력이다 — `GetWeatherAt`이 세이브 생성 시각 이전을 조회할 정상 흐름은 없어야 하므로(오프라인 진행 계산은 항상 `lastUpdatedUtc ≥ scheduleStartUtc`를 전제), 방어적으로 `scheduleStartUtc`로 clamp한 뒤 `n=0`(Sunny) 구간 결과를 반환한다. 이 경로가 실제로 트리거된다면 세이브/영속성 시스템의 구조적 유효성 검사(`lastUpdatedUtc`)가 먼저 실패했어야 한다는 신호다.
- **If 조회 시각 `T`가 구간 경계와 정확히 일치하면(`T = segStart(n) + Duration(n)`)**: 그 시각은 **다음 구간**(`n+1`)에 속한다 — 반열림구간 `[segStart, segEnd)` 컨벤션. §3 의사코드의 `if segStart + d > T: return` 조건이 이미 이 컨벤션을 구현한다(등호일 때 조건이 거짓이라 루프가 계속 진행됨). §0의 PRNG `[0,1)` 반열림 컨벤션과 동일한 원칙을 경계에도 일관되게 적용한 것뿐, 별도 신규 규칙 아님.
- **If `n=0`(최초 날씨) 구간을 조회하면**: `SelectNext`를 호출하지 않고 `H(seed, 0, 'sel')`도 소비하지 않는다(§2 최초 날씨 예외 재확인) — 구현 시 `n=0`에서 실수로 이 스트림을 소비하면 `n≥1`의 모든 후속 선택이 한 칸씩 밀려, 같은 시드라도 재현·QA 검증 시 다른 결과가 나온다.

### 오프라인/멀티디바이스 보장

- **If 오프라인 갭이 수년(예: 100년)에 달하면**: `GetWeatherAt`은 여전히 유한 시간 내 종료한다 — §3에서 유도한 상한(모든 구간이 최소 `DURATION_MIN=6h`일 때) `⌈(T - scheduleStartUtc) / 6⌉`회 루프면 충분하며, 100년 갭도 약 146,000회 반복(수 밀리초)에 그친다. 이 상한을 넘는 T는 존재하지 않으므로 캐시나 상한 없는 재귀가 필요 없다.
- **If 같은 세이브가 여러 디바이스에서 번갈아(또는 클라우드 동기화로) 열리면**: 각 디바이스가 독립적으로 계산한 `GetWeatherAt(seed, scheduleStartUtc, T)`는 항상 완전히 동일한 `(weather, segStart, segEnd)`를 반환한다 — 서버 권위나 락 없이도 일관성이 보장된다. 이는 §0의 PRNG 계약("같은 입력엔 항상 같은 출력")이 직접 함의하는 결과이며, 구현 시 이 함수에 디바이스 로컬 상태(현재 시각 이외의 캐시나 별도 랜덤 시드)를 섞으면 이 보장이 깨진다.

### 버전업 컷오버 (post-MVP 폭염 추가)

- **If MVP(3종 가중치) 세이브가 폭염 추가 버전으로 업데이트되면**: 가중치가 `{Sunny 0.50, RainFog 0.25, ColdSnap 0.25}`에서 `{Sunny 0.45, RainFog 0.20, ColdSnap 0.20, Heatwave 0.15}`로 바뀐다. `GetWeatherAt`은 매번 `n=0`부터 전체를 재계산하므로(캐시된 "현재 날씨" 없음 — Detailed Design 규칙 5), 손대지 않으면 아직 지나가지 않은 구간뿐 아니라 **이미 지나간 과거 구간의 재해석 결과도** 새 가중치로 바뀐다. 과거에 실제 적용된 감쇠 효과(potato-stat에 이미 반영된 값)가 되돌아가지는 않지만, 같은 과거 구간을 두 번째로 조회(재시도·검증 등)하면 업데이트 전후로 다른 답을 받게 되어 "결정론적 재구성" 전제가 깨진다.
  **해소 규칙**: 업데이트 적용 시각을 `cutoverUtc`로 고정 기록하고, `GetWeatherAt`은 `segStart(n) < cutoverUtc`인 구간에는 항상 구버전(3종) 가중치를, `segStart(n) ≥ cutoverUtc`인 구간에는 신버전(4종) 가중치를 적용한다 — PRNG 스트림(`H(seed,n,salt)`)과 `n` 인덱싱 자체는 그대로이고, 가중치 테이블만 "시드당 상수"에서 "컷오버 기준 구간별 상수"로 확장된다.
- **If 컷오버 경계에 걸친 구간에 §2의 연속 반복 금지 규칙(겨냥 스탯 기준)을 적용해야 하면**: 문제 없다 — MVP 3종은 모두 post-MVP 4종의 부분집합이라 `target(w_n)`은 컷오버 전후 어느 쪽 구간에서도 항상 유효하며, 규칙이 별도 예외 없이 그대로 적용된다.
- **If `cutoverUtc`가 세이브에 기록되지 않은 채로 로드되면(마이그레이션 누락)**: `weather_schedule_seed` 등록 항목에 `cutoverUtc` 서브필드가 없는 구버전 세이브로 간주하고, **로드 시각을 `cutoverUtc`로 채택**한다(컷오버가 "지금 막 일어난 것"으로 취급) — 과거 재해석 위험을 로드 시점 이전 전체로 완전히 차단하는 가장 보수적인 값이다.

## Tuning Knobs

| 노브 | 기본값 | 안전 범위 | 너무 낮으면 | 너무 높으면 |
|---|---|---|---|---|
| `DURATION_MIN` | 6h | 3~8h(`DURATION_MAX`보다 항상 최소 2h 이상 작아야 균등분포가 의미를 가짐) | 날씨가 너무 자주 바뀌어(예: 1h) 세션 중간에도 여러 번 전환 — Pillar 4 "짧게 자주 부담없이"가 오히려 산만함으로 느껴짐 | `DURATION_MAX`에 근접하면 지속시간 분포가 사실상 상수가 되어 "매번 다른 날" 체감이 사라짐 |

| `WEIGHT_RAINFOG`/`WEIGHT_COLDSNAP` | 0.25/0.20, 서로 대칭 유지 | 0.15~0.30, 두 값은 항상 동일하게(스탯 편애 방지) | 특정 스탯(습도/온도)이 거의 안 나와 그 케어 제스처(창문/난로) 존재감 저하 | 특정 스탯이 과대표집되어 나머지 스탯 케어가 소외됨 |
| `WEIGHT_HEATWAVE`(post-MVP) | 0.15 | 0.05~0.20(`WEIGHT_SUNNY`를 절대 넘지 않아야 "심각할수록 희소하게" 원칙 유지) | 폭염의 서사적 특별함(가장 드문 이벤트)이 옅어짐 | §6 시나리오 D(정정 전 허점)처럼 폭염 연속 노출 확률이 올라가 안전 여유가 줄어듦 — §6 재검증 필수 |

**노브 간 상호작용**:
- `DURATION_MAX`와 `ACTIVE_RATE_HEATWAVE`(또는 임의의 `ACTIVE_RATEᵢ`)는 함께 §6("복합 방치 리스크 검증")의 안전 주장을 구성한다 — 둘 중 하나라도 바뀌면 §6의 적대적 시나리오(A~E)를 재실행해 "하루 2회 체크인은 항상 안전" 약속이 깨지지 않는지 재확인해야 한다.
- `WEIGHT_*`는 절대값이 아니라 **상대 비율**만 의미를 가진다 — §2의 조건부 확률이 매 선택마다 후보 집합을 재정규화(합=1)하므로, 모든 가중치를 2배로 늘려도 결과 분포는 동일하다.
- `DURATION_MIN`/`DURATION_MAX`를 바꾸면 §1의 "평균 지속시간 8h ≈ Pillar 4 체크인 리듬" 근거(`(MIN+MAX)/2`)도 재검토해야 한다.

## Visual/Audio Requirements

> 이 섹션은 새로운 아트 방향을 정의하지 않는다 — `art-bible.md` Section 2(날씨 이벤트)가

> 계약**뿐이다(art-director 상담, 2026-07-15).

### 1. 상태별 무드 (art-bible Section 2 인용, 신규 아님)

| 날씨 | 광원/색온도 | 에너지 레벨 | 고유 오버레이 요소 |
|---|---|---|---|
| Sunny(맑음) | 따뜻한 크림/버터옐로, 대비 낮음~중간 | 정적 관조 | 정지된 옅은 햇살 번짐 워시 |
| RainFog(폭우/안개) | 차가운 회청빛, 대비 의도적으로 낮춤(전 상태 중 가장 차가움) | 잔잔한 | 반투명 안개 워시(창문 터치 시 해당 부분만 걷힘) |
| ColdSnap(한파/폭설) | 차가운 페일 블루-화이트, 하이키·저대비·최저 채도 | 정적 관조(전체 중 가장 조용함) | 마른붓 텍스처 눈 쌓임, 난로 터치 시 주황 글로우 |
| Heatwave(폭염, post-MVP) | 따뜻한 오커/앰버, 하이라이트 대비는 맑음보다 높음 | 조용한 다급함(baseline보다 유일하게 한 단계 높음) | 갈라진 마른 흙 + 극저속 아지랑이 왜곡, 물뿌리개 터치 시 김 이펙트 |

구도·오브젝트 배치·화풍·광원 방향(좌상단 45°)은 4개 상태 전부 동일 — 변하는 것은
색온도·대비·오버레이 하나뿐(art-bible 원칙, 재확인만).

### 2. 전환 크로스페이드 계약 (신규 — Formulas §5가 넘긴 결정)

날씨 구간 경계(`segEnd(n)`, §3)에서 스탯 감쇠율은 계단함수로 즉시 바뀌지만(Formulas §5,
불변), 화면 무드는 아래 계약에 따라 별도로 부드럽게 전환된다.

| 상수 | 값 | 설명 |
|---|---|---|
| `CROSSFADE_DURATION` | 3.0s | 색온도 그레이드(URP 전역 포스트프로세스 1패스, Asset Standards §8 기존 메커니즘 재사용) 전체 크로스페이드 길이 |
| `OVERLAY_FADE_OUT` | 0–1.2s | 기존 날씨 고유 오버레이(안개/눈/아지랑이/햇살번짐) 페이드아웃 구간 |
| `OVERLAY_FADE_IN` | 1.2–3.0s | 신규 날씨 오버레이 페이드인 구간(페이드아웃과 겹치지 않음 — 동시에 두 오버레이가 부분 알파로 공존하지 않는다) |

**핵심 규칙**:
1. **라이브 전환에만 재생**: 앱이 실제로 열려 있는 상태에서 경계를 실시간으로 통과할
   때만 위 크로스페이드를 재생한다. 앱이 닫혀 있던 동안 경계를 지난 경우(§3
   `GetWeatherAt` 오프라인 재구성), 다음 앱 실행 시 새 상태를 **즉시 스냅**으로
   표시한다 — 아무도 보지 않는 전환에 애니메이션을 소비하지 않는다(모바일 배터리
   효율, `technical-preferences.md`와 일치).
2. **터치 반응이 항상 우선**: 날씨 전환과 터치 케어 인터랙션(창문/난로/물뿌리개의
   번짐 애니메이션)이 동시에 발생해도, 터치 피드백은 절대 지연·중단되지 않는다 —
   서로 다른 레이어(전역 포스트프로세스 vs. 로컬 오브젝트 애니메이션)라 시각적으로
   경합하지 않는다.
3. **Rewind&Recovery와의 차이(의도적)**: art-bible Section 4(되돌리기/회복)의
   "의도적으로 느린" 크로스페이드는 드문 서사적 순간을 위한 것이다. 날씨 전환은
   6~10h마다 반복되는 일상적 이벤트이므로 같은 무게의 느린 연출을 쓰지 않는다 — 3초는
   팝/플래시를 피할 만큼 충분히 길되, "정적인 포근함"의 배경 등급을 벗어나지 않을
   만큼 짧다.

### 3. 오디오 (범위 메모)

이 시스템은 사운드를 직접 재생하지 않는다. `GetCurrentWeather()`(Dependencies 참고)가
노출하는 현재 날씨 enum이 ASMR 적응형 오디오 시스템(별도 GDD, 아직 미설계)이 구독할
유일한 훅이다 — 날씨별 앰비언트 사운드 팔레트 자체의 설계는 그 GDD의 몫이다.

## UI Requirements

이 시스템은 전용 HUD 요소를 갖지 않는다 — 날씨는 화면 전체 무드(Visual/Audio
Requirements §1~2)로 표현되며, 이것이 곧 Overview가 말하는 "앱을 열 때 가장 먼저
확인하게 되는 첫인상"이다. 별도의 날씨 아이콘·배지·텍스트 라벨을 화면에 추가하지
않는다 — art-bible UI/HUD Iconography §3의 "날씨 위젯은 신규 픽토그램 대신 감자
실루엣 재사용" 원칙과 일치한다.

유일하게 관련된 UI 표면은 OS 홈 화면 위젯/알림 트레이 아이콘(art-bible UI/HUD §6)이며,
이미 그 문서가 소유·확정한 영역이다 — 이 시스템은 `GetCurrentWeather()`(Dependencies
참고)로 현재 날씨 enum을 노출하는 것 외에 추가로 할 일이 없다. 위젯의 배경 자체가
날씨색을 반영할지 여부는 art-bible이 아직 명시하지 않은 지점이라 Open Questions로
넘긴다.

## Acceptance Criteria

> *(`qa-lead` 상담 완료 — lean 모드에서도 Acceptance Criteria는 상담 필수 섹션. §6 관련
> 항목은 이후 systems-designer 재상담으로 완전히 재검증된 수치를 반영했다 — 위 Formulas
> §6 갱신 참고. 새 ID 패밀리 `AC-INT-##`은 이 GDD가 처음 도입한다(호출 라우팅·세이브
> 등록 계약 전용, potato-stat이 담당하는 스탯 산술과 분리).)*

### 스케줄링 & 선택 (§0~§2)

- **AC-F-01 (PRNG 결정성)** **GIVEN** `seed=42, n=5, salt='dur'` **WHEN** `H(42,5,'dur')`를 서로 다른 시점에 두 번 호출 **THEN** 두 호출 모두 정확히 `0.42`를 반환한다.
- **AC-F-02 (지속시간 공식과 범위)** **GIVEN** `seed=42, n=5, H(42,5,'dur')=0.42` **WHEN** `Duration(5)` 계산 **THEN** `7.68h`이고, 임의의 `H∈[0,1)`에 대해 `6 ≤ Duration(n) < 10`.
- **AC-F-03 (최초 날씨 고정 및 PRNG 미소비)** **GIVEN** 임의의 `seed` **WHEN** `Weather(0)` 조회 **THEN** `Sunny`(고정)이고 `H(seed,0,'sel')` 호출 횟수 = 0.
- **AC-F-04 (다음 날씨 후보 — 겨냥 스탯 기준 제외, MVP)** **GIVEN** `Weather(5)=RainFog(target=습도)`, MVP 가중치 **WHEN** `n=6` 후보 계산 **THEN** 후보 `={Sunny 0.667, ColdSnap 0.333}`(재정규화).
- **AC-F-05 (동일 타겟 이중 제외, post-MVP)** **GIVEN** post-MVP 4종, `Weather(n)=Sunny(target=수분)` **WHEN** `n+1` 후보 계산 **THEN** Sunny와 Heatwave 모두 제외, 후보 `={RainFog, ColdSnap}`.
- **AC-F-06 (H값 → 최종 날씨 매핑)** **GIVEN** CDF `={Sunny[0,0.667), ColdSnap[0.667,1)}` **WHEN** `H(seed,6,'sel')=0.83` **THEN** `Weather(6)=ColdSnap`.

### GetWeatherAt 결정론 (§3)

- **AC-F-07 (정상 구간 조회)** **GIVEN** 문서 예시 스케줄(구간0 Sunny/구간1 RainFog/구간2 ColdSnap) **WHEN** `GetWeatherAt(2026-07-01T20:00Z)` **THEN** `(ColdSnap, 14:30, 23:42)`.
- **AC-F-08 (반열림구간 경계)** **GIVEN** `T`가 어느 구간의 `segEnd`와 정확히 일치 **WHEN** `GetWeatherAt(T)` **THEN** 반환 구간은 `n+1`이다.
- **AC-F-09 (멀티디바이스 동일 결과)** **GIVEN** 동일한 `(seed, scheduleStartUtc, T)` **WHEN** 서로 다른 프로세스에서 독립 호출 **THEN** 결과가 완전히 동일하다.
- **AC-F-10 (100년 갭 유한 루프 종료)** **GIVEN** `T=scheduleStartUtc+100년` **WHEN** `GetWeatherAt(T)` **THEN** 약 146,000회 이내 종료, 유효한 결과 반환.

### 폭염 감쇠율 계약 (§4)

- **AC-F-11 (폭염 ACTIVE_RATE 계약)** **GIVEN** 활성 날씨`=Heatwave(target=수분)` **WHEN** `rate(수분,t)` 조회 **THEN** `-4.0 pts/hr` 반환, `AdjustMoisture` 델타로 그대로 전달(클램프·시듦 임계값은 potato-stat `AC-F-17~21`이 검증).

### 즉시 전환 (§5)

- **AC-F-12 (전환 시 계단형)** **GIVEN** 습도=65, `t=8h`에 RainFog(+2.5)→ColdSnap(비겨냥,+0.5) 전환 **WHEN** `t=8h` 전후·`t=14h` 측정 **THEN** `V(8⁻)=V(8⁺)=65`(연속), rate 즉시 전환(보간 없음), `V(14)=68`.
- **AC-F-13 (구간 경계당 정확히 1회 전환)** **GIVEN** 전환 경계 `segEnd(n)` **WHEN** `rate(V,t)` 경계 전후 샘플링 **THEN** 정확히 1회만 변경, 다음 경계까지 상수.

### 복합 방치 리스크 검증 (§6, 2026-07-12 재검증 반영)

- **AC-F-14 (시나리오 A — 라운드로빈 최소지속시간)** **GIVEN** 맑음→폭우안개→한파 반복(전부 6h), Healthy·N=0 시작 **WHEN** 궤적 추적 **THEN** `T=26.97h` — 고립 벤치마크 대비 더 안전.
- **AC-F-15 (시나리오 C — 재현 가능한 형태로 고정)** **GIVEN** 맑음 6h(고정)↔폭우안개 10h(고정), Healthy·N=0 시작 **WHEN** 궤적 추적 **THEN** `T=24.04h` — 더 안전.
- **AC-F-16 (평균적 라운드로빈)** **GIVEN** 맑음(0-8h)→폭우안개(8-16h)→한파(16-24h) **WHEN** `t=24h` 확인 **THEN** `N(24)≈24/100`.
- **AC-F-17 (12시간 체크인 — 전역 최댓값)** **GIVEN** 도달 가능한 임의 스케줄(`Weather_0=맑음` 고정 포함), Healthy·N=0 시작 **WHEN** `t=12h` 확인 **THEN** `N(12) ≤ 0.90` — 증명된 전역 최댓값(근사 아님), "하루 2회 체크인은 항상 안전" 약속이 강하게 유지됨.

### Interactions & Save Contract

- **AC-INT-01 (겨냥 스탯 라우팅)** **GIVEN** 활성 날씨`=Sunny(target=수분)` **WHEN** 1시간 경과 **THEN** `AdjustMoisture`만 호출, `AdjustHumidity/AdjustTemperature` 미호출.
- **AC-INT-02 (비겨냥 스탯 미호출 — 폭염 예)** **GIVEN** 활성 날씨`=Heatwave(target=수분)` **WHEN** 1시간 경과 **THEN** `AdjustHumidity, AdjustTemperature` 미호출.
- **AC-INT-03 (세이브 시 기준점만 등록)** **GIVEN** 세이브 트리거 **WHEN** 직렬화 데이터 조회 **THEN** `weather_schedule_seed({seed, scheduleStartUtc, cutoverUtc?})`만 등록, "현재 날씨" 별도 필드 없음.
- **AC-INT-04 (로드 후 재계산 일관성)** **GIVEN** 세이브된 `{seed, scheduleStartUtc}`, 로드 시각 `T` **WHEN** 로드 직후 `GetWeatherAt(T)` **THEN** 세이브 전 동일 계산과 정확히 동일.

### Edge Cases

- **AC-EC-01 (T<scheduleStartUtc 클램프)** **GIVEN** `T<scheduleStartUtc` **WHEN** `GetWeatherAt(T)` **THEN** clamp 후 `n=0`(Sunny) 반환, `SelectNext`/`H(seed,0,'sel')` 미호출.
- **AC-EC-02 (cutoverUtc 전/후 가중치 분기)** **GIVEN** `cutoverUtc` 설정 **WHEN** 각 구간 SelectNext 평가 **THEN** 컷오버 이전 구간은 MVP 3종, 이후는 post-MVP 4종 가중치 사용.
- **AC-EC-03 (cutoverUtc 미설정 시 로드시각 채택)** **GIVEN** post-MVP 빌드 로드, `cutoverUtc` 없음 **WHEN** 로드 처리 **THEN** `cutoverUtc`가 로드 시각으로 설정.
